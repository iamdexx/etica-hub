# Research markets — auto-Sourcify pipeline

This doc describes how every `ResearchToken` launched by the
`EticaResearchMarkets` singleton gets its source code published to
Sourcify automatically, with zero manual intervention by the researcher.

## Why auto-Sourcify

Research tokens are funding instruments for scientific work. Buyers are
trusting that the token they hold has no hidden mint, pause, transfer
tax, blacklist, or upgrade. The most reliable way to demonstrate that —
short of an audit per token — is to:

1. Freeze the `ResearchToken` bytecode behind a single, audited
   template, and
2. Have an independent third party (Sourcify) confirm that every
   on-chain token's bytecode is an exact match of that template.

This shifts the trust model from "trust the researcher" to "trust the
template and Sourcify's matcher." It also closes a real MEV vector:
unverified tokens can quietly include backdoor mint or transfer-block
hooks that drain liquidity once price discovery starts. Sourcify
verification at launch makes that class of attack impossible to hide.

## Determinism

`ResearchToken.sol` is a plain `ERC20Permit` whose only varying state
across launches is its constructor arguments (the metadata struct, the
`market` address, and `researcher`). The bytecode itself is
byte-identical. This is enforced architecturally:

- the contract has no `Ownable`, `AccessControl`, or pause logic
- mint and burn are restricted to `market` (the singleton)
- there is no `transferTax`, `blacklist`, `feeOnTransfer`, or rebase
- there is no proxy / upgrade / `delegatecall` path

Because the bytecode is fixed, **one canonical Sourcify bundle**
verifies every launched token. The bundle is committed at:

```
packages/contracts/sourcify-bundles/ResearchToken/
├── standard-input.json   # Solidity standard-input.json for v2/verify
└── info.json             # compilerVersion + identifier + settings
```

It is regenerated by:

```bash
cd packages/contracts
node scripts/build-sourcify-bundle.mjs src/research-markets/ResearchToken.sol ResearchToken
```

The builder walks imports from disk, resolves `foundry.toml` remappings,
and emits a Sourcify-compatible JSON. Re-run only if
`ResearchToken.sol` or its import graph changes. After re-running, redo
the singleton + recompile so on-chain bytecode and the bundle agree.

## How the cron works

`apps/research-markets-sourcify/` is a small Node worker (modeled on
`apps/labs-autopilot/`). One tick:

1. Reads the `EticaResearchMarkets` singleton address from
   `packages/shared/src/addresses.ts`.
2. Reads `Launched(token, ...)` events from a sliding window of the
   last ~50_000 blocks (configurable via `RESEARCH_SOURCIFY_LOOKBACK`).
3. For each unique token: `GET {SOURCIFY_SERVER}/v2/contract/{chainId}/{addr}`.
   - `404` → not yet verified, submit
   - `200` → already verified, skip
   - `400/422/501` → chain not supported, abort this tick clean
4. For each token still needing verification:
   `POST {SOURCIFY_SERVER}/v2/verify/{chainId}/{addr}` with the
   canonical `standard-input.json`, the long-form compiler version
   (e.g. `0.8.26+commit.8a97fa7a`), and `contractIdentifier`.

The worker is fully stateless. There is no checkpoint file, no orphan
branch, no Redis. Sourcify itself is the source of truth — every tick
re-derives the set of tokens that still need submission, so retries
and partial failures are idempotent.

GitHub Actions schedule: `*/10 * * * *` (every 10 min). Manual
dispatch is available at:
`https://github.com/iamdexx/etica-hub/actions/workflows/research-markets-sourcify.yml`.

## Etica mainnet (chain 61803) Sourcify support

At time of writing, chain 61803 is not yet supported by the public
Sourcify server. The worker handles this gracefully — it detects the
`400/422/501` response, logs the body, and exits clean. Once the
upstream chain-add PR ([argotorg/sourcify#2758][add-pr]) merges, the
cron will start producing successful submissions on the next tick
without any code change here.

In the meantime, the existing manifest-based explorer at
`eticahub.com/explorer` shows source for every verified contract via
the same standard-input bundle (see
`apps/web/scripts/verify-contract.mjs`). The Sourcify pipeline is
strictly additive: it gives us a second, fully independent verification
surface once Sourcify supports the chain.

## UI surfacing

`/research-markets/[token]` shows a live Sourcify status badge in the
"Provenance" card via
`apps/web/src/components/research-markets/SourcifyBadge.tsx`. The badge
queries the Sourcify server directly on render and shows one of:

- **Sourcify verified ✓ exact** — green, links to the repo entry
- **Sourcify verified ✓** — green (partial match, links to repo)
- **Pending Sourcify verification** — amber (cron hasn't picked it up yet)
- **Chain pending Sourcify support** — zinc (chain 61803 not yet listed)

## Required env / GitHub Actions config

The cron uses **repo variables** (not secrets), since the worker only
calls public RPC + public Sourcify endpoints:

| Variable                       | Default                              | Purpose                                                 |
| ------------------------------ | ------------------------------------ | ------------------------------------------------------- |
| `RESEARCH_SOURCIFY_RPC_URL`    | `https://eticamainnet.eticascan.org` | Etica RPC used to read `Launched` events                |
| `RESEARCH_SOURCIFY_SERVER`     | `https://sourcify.dev/server`        | Sourcify v2 server base URL                             |
| `RESEARCH_SOURCIFY_LOOKBACK`   | `50000`                              | Block window for event reads (~7d at 12s blocks)        |
| `RESEARCH_SOURCIFY_SINGLETON`  | _empty_                              | Override addresses.ts singleton lookup (rarely needed)  |

No secrets are required for ordinary operation. If you need to point
the cron at a self-hosted Sourcify instance with auth, add a Bearer
header in `apps/research-markets-sourcify/src/worker.ts`.

## Manual verification fallback

If the cron is paused or you want to verify ad-hoc, hit the same
endpoint the worker uses from any wallet/box that has the bundle:

```bash
curl -X POST \
  -H 'Content-Type: application/json' \
  --data @<(jq -n \
    --arg ver "$(jq -r .compilerVersion packages/contracts/sourcify-bundles/ResearchToken/info.json)" \
    --arg id "$(jq -r .contractIdentifier packages/contracts/sourcify-bundles/ResearchToken/info.json)" \
    --slurpfile std packages/contracts/sourcify-bundles/ResearchToken/standard-input.json \
    '{stdJsonInput: $std[0], compilerVersion: $ver, contractIdentifier: $id}') \
  https://sourcify.dev/server/v2/verify/61803/<token-address>
```

Or use the existing app endpoint at
`POST /api/explorer/sourcify/verify`, which proxies the call server-side.
